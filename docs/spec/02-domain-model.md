Модель собрана только из названных в ТЗ данных. Поля, которых нет в ТЗ, сюда не добавлены.

## Subscriber

Подписчик в нашей базе.

- Идентификатор в обменах с Platform: `subscriberId`.
- На входе opt-in ТЗ говорит «takes an MSISDN» (строка 40).
- Статусы, названные прямо:
  - **ACTIVE** — после успешного opt-in (строка 41). Дневной job списывает только ACTIVE (строка 52).
  - **INACTIVE** — после opt-out (строка 62). Больше не списывать (строки 63–64, 111).
- **suspend** на `E1308` (строки 57, 194) — обязательное действие. Имя статуса в ТЗ не зафиксировано. Принятый Q4: `SUSPENDED`, рядом с `ACTIVE` и `INACTIVE`. Возврата из `SUSPENDED` в MVP нет. Схема T-1.1 уже так и записана.

Уже ACTIVE нельзя подписать повторно (строка 43).

## Charge attempt

Каждая попытка списания сохраняется и доступна для выборки (строки 83–85). Обязательные атрибуты записи:

- status (код результата попытки);
- `externalTrxId`;
- `referenceId`;
- timestamp.

Один ACTIVE-подписчик — не больше одного списания за billing day (строки 52–58, 73–74), в том числе при повторе job, ретраях и рестартах.

Связь: charge attempt принадлежит подписчику. Успешная попытка (`S1000`) имеет `referenceId` из ответа Platform. Для неуспеха ТЗ требует сохранить попытку; `referenceId` в ответе ошибки не описан.

## Subscription notification

Входящее событие §B. Поля: `applicationId`, `subscriberId`, `frequency`, `status`, `version`, `timeStamp`. `status` одно из `REGISTERED | UNREGISTERED | PENDING | CHARGE`.

То же событие дважды не меняет состояние разрушительно и не вызывает лишнее списание (строки 48–49, 109).

## SMS

- Исходящие MT: welcome (F1), receipt с `referenceId` (F3), goodbye (F4).
- Входящая MO: `STOP` запускает opt-out (F4).

Текст сообщений, `sourceAddress` и `encoding` для MO в ТЗ не заданы. Контракт полей — `modules/sms.md`.

## Платформенные статусы подписки

Ответ §A: `subscriptionStatus` = `REGISTERED` при opt-in и `UNREGISTERED` при opt-out (строки 152–153). Это статус Platform, не синоним, явно приравненный в ТЗ к ACTIVE/INACTIVE.
