# Вопросы и допущения

Источник пометок — только то, чего нет или что неоднозначно в `ASSIGNMENT_SHORT.md`. Пока статус `draft`, ни один вариант по умолчанию не является требованием.

## Вопросы

### Q1. Граница billing day
- Блокирует: T-1.5, T-3.3 и любые задачи про «один раз в день».
- В ТЗ: списание at most once per billing day. Часовой пояс и граница суток не заданы.
- Вариант по умолчанию: календарная дата UTC. `externalTrxId` стабилен внутри этой даты.

### Q2. Сумма и валюта дневной платы
- Блокирует: T-3.3 (тело Direct Debit).
- В ТЗ: «fixed daily fee» без числа. В примере §D `amount` `"5.00"`, `currency` `"XTS"`. Multi-currency вне скоупа.
- Вариант по умолчанию: одна плата `5.00` `XTS`, значение из env, не захардкожено.

### Q3. Числа grace / retry / backoff
- Блокирует: T-3.4, T-3.5.
- В ТЗ: bounded retries with backoff; `E1326` → grace/retry; `E1318` → throttle/backoff. Сколько попыток и какие паузы — нет.
- Вариант по умолчанию: не больше 3 попыток на один `externalTrxId` в тот же billing day; пауза 1 с, 2 с, 4 с. Новый `externalTrxId` не создавать. После исчерпания попыток попытка остаётся неуспешной, подписчик при `E1326` остаётся ACTIVE (его можно списать позже в тот же день тем же ключом, если job запустят снова — это всё ещё один логический charge). Для `E1318` та же схема backoff.

### Q4. Статус suspend
- Блокирует: T-1.1 (схема), T-3.4.
- В ТЗ: `E1308` → suspend. Opt-out → INACTIVE. Отдельного имени и сценария возобновления нет.
- Вариант по умолчанию: три статуса `ACTIVE`, `SUSPENDED`, `INACTIVE`. Job списывает только `ACTIVE`. Возврата из `SUSPENDED` в MVP нет.

### Q5. Эффект webhook на локальное состояние
- Блокирует: T-3.6.
- В ТЗ: handle at least `REGISTERED` и `UNREGISTERED`; статус ещё бывает `PENDING` и `CHARGE`; дубль не списывает и не портит состояние. Переходы не заданы.
- Вариант по умолчанию: `REGISTERED` приводит локальную запись к `ACTIVE` и не шлёт второй welcome, если welcome уже был. `UNREGISTERED` приводит к `INACTIVE` и не шлёт второй goodbye. `PENDING` и `CHARGE` только сохраняются как событие и отвечают `S1000`, без списания и без смены статуса. Webhook никогда не вызывает Direct Debit.

### Q6. Форма HTTP API сервиса
- Статус: принято 2026-11-23. UI не делаем.
- Блокирует: T-3.1, T-3.2, T-3.7, T-3.8, README. Больше не блокирует: решение есть.
- В ТЗ: «HTTP endpoint or UI action», «an endpoint» для статуса, «curl или CLI или tiny UI». Пути не заданы.
- Решение: только HTTP-эндпоинты. Сценарии гоняются задокументированными `curl`. CLI и tiny UI не строим.
  - `POST /subscribers` тело `{"msisdn":"tel:..."}` — opt-in.
  - `GET /subscribers/{subscriberId}` — текущий статус.
  - `POST /jobs/daily-charge` — ручной job.
  - `POST /webhooks/subscription` — §B.
  - `POST /webhooks/mo` — §C.
  - `GET /charges?msisdn=&date=` — ответ аудита «списан ли сегодня и какой reference».

### Q7. Тексты SMS и sourceAddress
- Блокирует: T-3.1, T-3.3, T-3.7.
- В ТЗ: welcome, receipt с `referenceId`, goodbye. Тексты и `sourceAddress` не заданы. `encoding` MT в примере `"0"`.
- Вариант по умолчанию: `sourceAddress` из env. Тексты фиксированные: welcome «Daily Pass is active»; receipt «Charged. Reference: {referenceId}»; goodbye «Daily Pass is stopped». `encoding` = `"0"`.

### Q8. Валидация MSISDN и masked alias
- Блокирует: T-1.2.
- В ТЗ одновременно: валидировать MSISDN как `tel:` + digits и не считать, что из `subscriberId` можно разобрать телефон, потому что это может быть стабильный masked alias.
- Вариант по умолчанию: на нашем входе opt-in требовать `^tel:[0-9]+$`. Значение целиком сохранять как `subscriberId` и передавать в Platform как есть. Нигде не отделять цифры «как номер телефона» и не нормализовать страну. Тот же шаблон принимать и для alias: alias тоже выглядит как `tel:` + стабильные цифры/не цифры? ТЗ говорит «not a real number» и «don't parse a phone number out of it», но пример только `tel:1000000001`. Уточнение по умолчанию: не требовать, чтобы цифры были валидным телефонным планом; требовать только префикс `tel:` и непустой хвост без пробелов. Хвост не интерпретировать.

Это сильнее, чем буквальное «tel: + digits». Если хвост alias может содержать не только цифры, проверка «digits» из строки 79 сломает alias. Поэтому вопрос остаётся открытым: **хвост masked alias — только цифры или произвольная стабильная строка?** Дефолт для старта, если не ответят иначе: `^tel:[0-9]+$`, как написано в строке 79, и запрет любой другой интерпретации хвоста.

### Q9. Повторный opt-in уже ACTIVE
- Блокирует: T-3.1.
- В ТЗ: must not be double-subscribed. Не сказано, вызывать ли Platform ещё раз и слать ли второй welcome.
- Вариант по умолчанию: если локально уже ACTIVE — не вызывать Platform и не слать второй welcome; вернуть текущее состояние.

### Q10. Идентичность события webhook
- Блокирует: T-3.6.
- В ТЗ: «the same event delivered twice». Состав ключа не задан.
- Вариант по умолчанию: ключ = `subscriberId` + `status` + `timeStamp` + `frequency`. Повтор с тем же ключом — no-op и снова `S1000`.

### Q11. Ответ `E1337`, если локального успеха нет
- Блокирует: T-3.5.
- В ТЗ: `E1337` non-retry-able, тот же `externalTrxId` — дубль. Тело ошибки не задано. Не сказано, слать ли receipt.
- Вариант по умолчанию: не создавать новый `externalTrxId` и не вызывать debit снова. Если в ответе есть `referenceId` — сохранить его. Если нет — записать попытку со статусом `E1337` без receipt. Второй charge не создавать.

### Q12. Повторный STOP и неизвестный абонент
- Блокирует: T-3.7.
- В ТЗ нет.
- Вариант по умолчанию: неизвестный `sourceAddress` — ответ MO `S1000`, без вызова Platform и без SMS (чтобы ретрай Platform не плодил побочные эффекты; это допущение). Уже INACTIVE — не вызывать Platform повторно и не слать второй goodbye.

### Q13. Как мок выбирает код списания
- Блокирует: T-2.3.
- В ТЗ: configurable, минимум `S1000`, `E1326`, `E1308`, `E1337`.
- Вариант по умолчанию: env `MOCK_CHARGE_STATUS` (один код на весь мок) плюс обязательное правило: уже виденный `externalTrxId` всегда отвечает `E1337`, даже если env сейчас другой. Так выполняется и «configurable», и дедуп ключа.

## Допущения

### A-STACK
ТЗ не задаёт язык. Для этого репозитория стек берётся из `.cursor/rules`: PHP ≥ 8.2, Yii2, Codeception, PHPStan, PHP-CS-Fixer, слои Domain / Application / Infrastructure / Presentation. И `service/`, и `platform-mock/` — PHP в образах Docker, чтобы на хосте не нужен был локальный runtime (REQ-OVW-004).

### A-DB
ТЗ требует сохранять подписчиков и попытки списания и уметь их выбирать. Тип СУБД не задан. По умолчанию PostgreSQL в том же `docker compose`, данные не на хосте.

### A-TIMEOUTS
В ТЗ нет чисел таймаута. По правилам проекта у HTTP-клиента к Platform будут явные connect/read timeouts. Это не меняет контракт.

### A-INSTRUMENT
В Direct Debit уходит `paymentInstrumentName` = `"Mobile Account"`, как в единственном примере §D.

### A-SMS-LOG
Мок хранит тела MT и отдаёт их для демо (иначе welcome не «виден в моке»). Конкретный путь чтения — часть T-2.2, не требование ТЗ сверх видимости.

### A-MOCK-E1318
§E обязывает сервис уметь обработать `E1318`. Список «at least» для мока этот код не включает. В MVP мок может его вернуть только если это дёшево; требованием ТЗ это не считается.

### A-NOAUTH
Эндпоинты демо без аутентификации пользователя: real auth/SSO вне скоупа. Секреты Platform при этом только в env.

### A-MANUAL-JOB
Фразы «scheduled or manually triggerable» достаточно ручного запуска. Cron не входит в MVP и не выбрасывается из ТЗ: это отложенный способ выполнить ту же REQ-CHG-001.

### A-ENTRY
Интерфейс сервиса — HTTP без UI (Q6, принято). Пути из Q6 — рабочий контракт демо, не цитата ТЗ.
