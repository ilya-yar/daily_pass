# Вопросы и допущения

Источник пометок — только то, чего нет или что неоднозначно в `ASSIGNMENT_SHORT.md`. Q6 принят отдельно. Q1–Q5 и Q7–Q13 приняты 2026-11-23: для каждого взят вариант по умолчанию. Эти решения больше не блокируют задачи.

## Вопросы

### Q1. Граница billing day
- Статус: принято 2026-11-23, вариант по умолчанию.
- В ТЗ: списание at most once per billing day. Часовой пояс и граница суток не заданы.
- Решение: календарная дата UTC. `externalTrxId` стабилен внутри этой даты.

### Q2. Сумма и валюта дневной платы
- Статус: принято 2026-11-23, вариант по умолчанию.
- В ТЗ: «fixed daily fee» без числа. В примере §D `amount` `"5.00"`, `currency` `"XTS"`. Multi-currency вне скоупа.
- Решение: одна плата `5.00` `XTS`, значение из env, не захардкожено.

### Q3. Числа grace / retry / backoff
- Статус: принято 2026-11-23, вариант по умолчанию.
- В ТЗ: bounded retries with backoff; `E1326` → grace/retry; `E1318` → throttle/backoff. Сколько попыток и какие паузы — нет.
- Решение: не больше 3 попыток на один `externalTrxId` в тот же billing day; пауза 1 с, 2 с, 4 с. Новый `externalTrxId` не создавать. После исчерпания попыток попытка остаётся неуспешной, подписчик при `E1326` остаётся ACTIVE (его можно списать позже в тот же день тем же ключом, если job запустят снова — это всё ещё один логический charge). Для `E1318` та же схема backoff.

### Q4. Статус suspend
- Статус: принято 2026-11-23, вариант по умолчанию. Схема T-1.1 уже использует эти три значения.
- В ТЗ: `E1308` → suspend. Opt-out → INACTIVE. Отдельного имени и сценария возобновления нет.
- Решение: три статуса `ACTIVE`, `SUSPENDED`, `INACTIVE`. Job списывает только `ACTIVE`. Возврата из `SUSPENDED` в MVP нет.

### Q5. Эффект webhook на локальное состояние
- Статус: принято 2026-11-23, вариант по умолчанию.
- В ТЗ: handle at least `REGISTERED` и `UNREGISTERED`; статус ещё бывает `PENDING` и `CHARGE`; дубль не списывает и не портит состояние. Переходы не заданы.
- Решение: `REGISTERED` приводит локальную запись к `ACTIVE` и не шлёт второй welcome, если welcome уже был. `UNREGISTERED` приводит к `INACTIVE` и не шлёт второй goodbye. `PENDING` и `CHARGE` только сохраняются как событие и отвечают `S1000`, без списания и без смены статуса. Webhook никогда не вызывает Direct Debit.

### Q6. Форма HTTP API сервиса
- Статус: принято 2026-11-23. UI не делаем.
- Блокирует: T-3.1, T-3.2, T-3.7, T-3.8, README. Больше не блокирует: решение есть.
- В ТЗ: «HTTP endpoint or UI action», «an endpoint» для статуса, «curl или CLI или tiny UI». Пути не заданы.
- Решение: только HTTP-эндпоинты. Сценарии гоняются задокументированными `curl`. CLI и tiny UI не строим.
  - `POST /subscribers` тело `{"msisdn":"tel:..."}` — opt-in.
  - `GET /subscribers/{subscriberId}` — текущий статус.
  - `POST /jobs/daily-charge` — ручной job.
  - `POST /webhooks/subscription` — §B.
  - `POST /webhooks/mo` — §C.
  - `GET /charges?msisdn=&date=` — ответ аудита «списан ли сегодня и какой reference».

### Q7. Тексты SMS и sourceAddress
- Статус: принято 2026-11-23, вариант по умолчанию.
- В ТЗ: welcome, receipt с `referenceId`, goodbye. Тексты и `sourceAddress` не заданы. `encoding` MT в примере `"0"`.
- Решение: `sourceAddress` из env. Тексты фиксированные: welcome «Daily Pass is active»; receipt «Charged. Reference: {referenceId}»; goodbye «Daily Pass is stopped». `encoding` = `"0"`.

### Q8. Валидация MSISDN и masked alias
- Статус: принято 2026-11-23, вариант по умолчанию.
- В ТЗ одновременно: валидировать MSISDN как `tel:` + digits и не считать, что из `subscriberId` можно разобрать телефон, потому что это может быть стабильный masked alias.
- Решение: на входе требовать `^tel:[0-9]+$`. Значение целиком сохранять как `subscriberId` и передавать в Platform как есть. Не отделять цифры «как номер телефона», не нормализовать страну и не проверять телефонный план. Хвост из не-цифр не принимается: дефолт совпадает со строкой 79 ТЗ, а не с более широким «любой хвост после `tel:`».

### Q9. Повторный opt-in уже ACTIVE
- Статус: принято 2026-11-23, вариант по умолчанию.
- В ТЗ: must not be double-subscribed. Не сказано, вызывать ли Platform ещё раз и слать ли второй welcome.
- Решение: если локально уже ACTIVE — не вызывать Platform и не слать второй welcome; вернуть текущее состояние.

### Q10. Идентичность события webhook
- Статус: принято 2026-11-23, вариант по умолчанию.
- В ТЗ: «the same event delivered twice». Состав ключа не задан.
- Решение: ключ = `subscriberId` + `status` + `timeStamp` + `frequency`. Повтор с тем же ключом — no-op и снова `S1000`.

### Q11. Ответ `E1337`, если локального успеха нет
- Статус: принято 2026-11-23, вариант по умолчанию.
- В ТЗ: `E1337` non-retry-able, тот же `externalTrxId` — дубль. Тело ошибки не задано. Не сказано, слать ли receipt.
- Решение: не создавать новый `externalTrxId` и не вызывать debit снова. Если в ответе есть `referenceId` — сохранить его. Если нет — записать попытку со статусом `E1337` без receipt. Второй charge не создавать.

### Q12. Повторный STOP и неизвестный абонент
- Статус: принято 2026-11-23, вариант по умолчанию.
- В ТЗ нет.
- Решение: неизвестный `sourceAddress` — ответ MO `S1000`, без вызова Platform и без SMS (чтобы ретрай Platform не плодил побочные эффекты). Уже INACTIVE — не вызывать Platform повторно и не слать второй goodbye.

### Q13. Как мок выбирает код списания
- Статус: принято 2026-11-23, вариант по умолчанию.
- В ТЗ: configurable, минимум `S1000`, `E1326`, `E1308`, `E1337`.
- Решение: env `MOCK_CHARGE_STATUS` (один код на весь мок) плюс обязательное правило: уже виденный `externalTrxId` всегда отвечает `E1337`, даже если env сейчас другой. Так выполняется и «configurable», и дедуп ключа.

## Допущения

### A-STACK
ТЗ не задаёт язык. Для этого репозитория стек берётся из `.cursor/rules`: PHP ≥ 8.2, Yii2, Codeception, PHPStan, PHP-CS-Fixer, слои Domain / Application / Infrastructure / Presentation. И `service/`, и `platform-mock/` — PHP в образах Docker, чтобы на хосте не нужен был локальный runtime (REQ-OVW-004).

### A-DB
ТЗ требует сохранять подписчиков и попытки списания и уметь их выбирать. Тип СУБД не задан. По умолчанию PostgreSQL в том же `docker compose`, данные не на хосте.

### A-TIMEOUTS
В ТЗ нет чисел таймаута. По правилам проекта у HTTP-клиента к Platform будут явные connect/read timeouts. Это не меняет контракт.

### A-INSTRUMENT
В Direct Debit уходит `paymentInstrumentName` = `"Mobile Account"`, как в единственном примере §D.

### A-SMS-LOG
Мок хранит тела MT и отдаёт их для демо (иначе welcome не «виден в моке»). Конкретный путь чтения — часть T-2.2, не требование ТЗ сверх видимости.

### A-MOCK-E1318
§E обязывает сервис уметь обработать `E1318`. Список «at least» для мока этот код не включает. В MVP мок может его вернуть только если это дёшево; требованием ТЗ это не считается.

### A-NOAUTH
Эндпоинты демо без аутентификации пользователя: real auth/SSO вне скоупа. Секреты Platform при этом только в env.

### A-MANUAL-JOB
Фразы «scheduled or manually triggerable» достаточно ручного запуска. Cron не входит в MVP и не выбрасывается из ТЗ: это отложенный способ выполнить ту же REQ-CHG-001.

### A-ENTRY
Интерфейс сервиса — HTTP без UI (Q6, принято). Пути из Q6 — рабочий контракт демо, не цитата ТЗ.
