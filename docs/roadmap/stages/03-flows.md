# Этап 3. Сценарии сервиса

Вертикальные срезы F1–F5. Числа retry, статусы и пути HTTP берутся из принятых Q1–Q13, не из догадки в момент кодирования.

### T-3.1: Opt-in
- Модуль: opt-in
- Требования: REQ-OPTIN-001, REQ-OPTIN-002, REQ-OPTIN-003, REQ-OPTIN-004, REQ-OPTIN-005, REQ-SMS-003, REQ-API-003
- Файлы ТЗ для контекста: `docs/spec/modules/opt-in.md`, `docs/spec/modules/sms.md`, `docs/spec/03-cross-cutting.md`
- Зависит от: T-1.1, T-1.2, T-1.4, T-2.1, T-2.2
- Затрагиваемые слои: Domain / Application / Infrastructure / Presentation
- Размер: M
- Что сделать:
  - Точка входа из принятого Q6 принимает MSISDN.
  - Невалидный идентификатор отвергается до вызова Platform.
  - Уже ACTIVE обрабатывается по принятому Q9.
  - Иначе: `POST /subscription/send` с `action:"1"`, при `S1000` сохранить ACTIVE и отправить welcome MT.
- Критерии приёмки:
  - Новый абонент становится ACTIVE, в моке виден welcome.
  - Повтор для ACTIVE не создаёт вторую подписку и, по Q9, не шлёт второй welcome.
  - Мусорный MSISDN не оставляет строку подписчика.
- Тесты: unit — решение «уже активен» без сети; api — opt-in против мока и отказ на мусоре.
- Сценарии сбоев: Platform не ответила → подписчик не становится ACTIVE, welcome не отправляется. Повторный вызов после такого сбоя можно выполнить снова (это ещё не double-subscribe). Таймаут не оставляет частично ACTIVE без успешного ответа.
- Статус: done

- Статус: done

### T-3.3: Успешное списание не больше одного раза в день
- Модуль: charging
- Требования: REQ-CHG-001, REQ-CHG-002, REQ-CHG-003, REQ-CHG-006, REQ-CHG-007, REQ-TEST-002, REQ-EVAL-001
- Файлы ТЗ для контекста: `docs/spec/modules/charging.md`, `docs/spec/03-cross-cutting.md`
- Зависит от: T-1.1, T-1.4, T-1.5, T-2.2, T-2.3, T-3.1
- Затрагиваемые слои: Domain / Application / Infrastructure / Presentation
- Размер: M
- Что сделать:
  - Ручной запуск job (REQ-CHG-001, A-MANUAL-JOB) берёт только ACTIVE.
  - На каждого считается `externalTrxId` дня и вызывается Direct Debit.
  - `S1000`: попытка сохранена, SMS receipt содержит `referenceId`.
  - Второй запуск в тот же billing day не создаёт второй успешный charge и не шлёт второй debit с новым ключом.
- Критерии приёмки:
  - Один ACTIVE, мок в `S1000`: одна успешная попытка, один receipt с тем `referenceId`, который вернул мок.
  - Второй запуск job в тот же день не увеличивает число успешных списаний.
  - INACTIVE в выборку не попадает (подготовка к F4; полная гонка — в T-3.7).
- Тесты: api — два запуска job против мока; unit — job не строит новый ключ на повторе.
- Сценарии сбоев: процесс падает после ответа `S1000`, но до записи попытки. Повтор job использует тот же `externalTrxId`; мок отвечает `E1337` или повторно отдаёт тот же результат, и вторая успешная строка не появляется. Рестарт сервиса не меняет ключ дня.
- Статус: done

### T-3.4: E1326 и E1308 обрабатываются по-разному
- Модуль: charging
- Требования: REQ-CHG-004, REQ-CHG-005, REQ-CHG-012, REQ-TEST-001, REQ-EVAL-003
- Файлы ТЗ для контекста: `docs/spec/modules/charging.md`, `docs/spec/open-questions.md` (Q3, Q4)
- Зависит от: T-1.3, T-3.3
- Затрагиваемые слои: Domain / Application
- Размер: M
- Что сделать:
  - `E1326`: ограниченный retry с backoff по принятому Q3, тот же `externalTrxId`. Подписчик не suspend.
  - `E1308`: не ретраить. Подписчик переходит в статус suspend из Q4. Новый ключ не выпускать.
  - Исчерпание попыток `E1326` не превращается в suspend.
- Критерии приёмки:
  - На `E1326` и `E1308` нет успешной транзакции и нет receipt.
  - После `E1308` следующий job этого абонента не вызывает debit.
  - После `E1326` абонент остаётся в статусе, из которого его ещё можно списать тем же ключом в этот billing day.
  - Число вызовов debit на один ключ не больше принятого лимита.
- Тесты: unit — классификация и лимит попыток на фейковом порте; api — мок отдаёт `E1326` и отдельно `E1308`.
- Сценарии сбоев: ретрай после таймаута идёт с тем же ключом. Non-retry-able не получает второй запрос с новым ключом. Конкурентный второй job в тот же день не обходит уникальный `externalTrxId`.
- Статус: done

### T-3.5: E1337 и E1318
- Модуль: charging
- Требования: REQ-CHG-009, REQ-CHG-010, REQ-CHG-011, REQ-CHG-012
- Файлы ТЗ для контекста: `docs/spec/modules/charging.md`, `docs/spec/open-questions.md` (Q3, Q11)
- Зависит от: T-1.3, T-2.3, T-3.3
- Затрагиваемые слои: Domain / Application
- Размер: M
- Что сделать:
  - `E1337`: не выпускать новый ключ и не слать ещё один debit. Запись попытки по правилу принятого Q11.
  - `E1318`: retry-able, backoff по Q3, тот же ключ.
- Критерии приёмки:
  - Ответ `E1337` не создаёт вторую успешную попытку и не вызывает debit с другим `externalTrxId`.
  - Серия `E1318` ограничена числом попыток и не помечает подписчика suspended.
- Тесты: unit — оба кода на фейковом порте, счётчик вызовов и значение ключа.
- Сценарии сбоев: `E1337` после рестарта, когда локальная строка успеха не успела записаться (Q11). Повтор не создаёт новый ключ.
- Статус: done

### T-3.6: Webhook подписки идемпотентен
- Модуль: subscription-webhook
- Требования: REQ-WH-001, REQ-WH-002, REQ-WH-003, REQ-WH-004, REQ-WH-005, REQ-TEST-003
- Файлы ТЗ для контекста: `docs/spec/modules/subscription-webhook.md`, `docs/spec/open-questions.md` (Q5, Q10)
- Зависит от: T-1.1, T-2.4, T-3.1
- Затрагиваемые слои: Application / Presentation
- Размер: M
- Что сделать:
  - Эндпоинт §B отвечает телом `statusCode` `S1000`, `statusDetail` `Success`.
  - `REGISTERED` и `UNREGISTERED` обрабатываются по принятому Q5.
  - `PENDING` и `CHARGE` не вызывают debit и не меняют статус сверх Q5.
  - Повтор того же события (ключ Q10) не меняет состояние второй раз и не списывает деньги.
- Критерии приёмки:
  - Два одинаковых POST подряд оставляют одного подписчика и ноль списаний, если charge job не запускали.
  - Ответ обоих вызовов — `S1000`.
  - Webhook не вызывает `POST /caas/direct/debit`.
- Тесты: api — дубль `REGISTERED` и дубль `UNREGISTERED` против мока; unit — ключ идемпотентности.
- Сценарии сбоев: второй запрос приходит после рестарта и видит уже записанное событие. Параллельные два одинаковых запроса не создают две активные подписки с двумя welcome, если Q5 запрещает повторный welcome.
- Статус: done

### T-3.7: STOP и гонка со списанием
- Модуль: opt-out
- Требования: REQ-OUT-001, REQ-OUT-002, REQ-OUT-003, REQ-OUT-004, REQ-OUT-005, REQ-OUT-006, REQ-SMS-002, REQ-TEST-001
- Файлы ТЗ для контекста: `docs/spec/modules/opt-out.md`, `docs/spec/modules/sms.md`, `docs/spec/modules/charging.md`
- Зависит от: T-2.1, T-3.1, T-3.3
- Затрагиваемые слои: Domain / Application / Presentation
- Размер: M
- Что сделать:
  - MO endpoint принимает поля §C и на сообщение `STOP` вызывает `/subscription/send` с `action:"0"`, ставит INACTIVE, шлёт goodbye.
  - Ответ MO — `S1000` / `Success`.
  - Списание проверяет статус так, чтобы opt-out, случившийся до фактического debit, не оставил успешный charge. Уже начатый debit не получает новый ключ на следующего абонента.
  - Следующий job пропускает INACTIVE.
- Критерии приёмки:
  - `STOP` переводит ACTIVE в INACTIVE, в моке есть goodbye, Platform получила action `"0"`.
  - Job после opt-out не создаёт успешную попытку.
  - Тест гонки: opt-out перекрывает in-flight charge, и успешных списаний этого дня нет либо единственное списание, которое Platform уже подтвердила до фиксации INACTIVE, не сопровождается вторым. Успешное списание после зафиксированного INACTIVE отсутствует.
- Тесты: api — STOP затем job; unit или integration — перекрывающиеся opt-out и charge на одном подписчике.
- Сценарии сбоев: opt-out не дождался Platform → локально не помечать INACTIVE (иначе мы перестанем списывать, а Platform останется REGISTERED) — это предлагаемое поведение, его подтвердить вместе с Q12, потому что ТЗ не описывает ошибку opt-out. Повторный `STOP` по Q12 не шлёт второй goodbye.
- Статус: todo
