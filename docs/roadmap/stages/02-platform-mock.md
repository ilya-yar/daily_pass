# Этап 2. Мок Platform

Мок отвечает по контракту и умеет ломать списание предсказуемо. Сервисные сценарии поверх него — этап 3.

### T-2.1: Мок POST /subscription/send
- Модуль: platform-mock, opt-in
- Требования: REQ-MOCK-001, REQ-API-002, REQ-API-003
- Файлы ТЗ для контекста: `docs/spec/modules/platform-mock.md`, `docs/spec/modules/opt-in.md`
- Зависит от: T-0.1
- Затрагиваемые слои: Presentation мока
- Размер: S
- Что сделать:
  - Принять JSON §A.
  - На `action:"1"` ответить примером успеха со `subscriptionStatus` `REGISTERED`.
  - На `action:"0"` ответить `UNREGISTERED`.
  - В ответе есть `statusCode`, `statusDetail`, `version`, `requestId`.
- Критерии приёмки:
  - Оба action дают коды и статусы из §A.
  - Иной action не выглядит как успешная регистрация.
- Тесты: api мока — opt-in и opt-out.
- Сценарии сбоев: битый JSON → не `S1000`.
- Статус: done

### T-2.2: Мок хранит исходящие SMS
- Модуль: platform-mock, sms
- Требования: REQ-MOCK-001, REQ-SMS-001, REQ-SMS-003
- Файлы ТЗ для контекста: `docs/spec/modules/sms.md`, `docs/spec/modules/platform-mock.md`
- Зависит от: T-0.1
- Затрагиваемые слои: Presentation мока
- Размер: S
- Что сделать:
  - `POST /sms/send` принимает поля §C и отвечает `statusCode` + `statusDetail`.
  - Сообщение сохраняется.
  - Есть способ прочитать сохранённые MT (A-SMS-LOG), чтобы welcome был виден при демо.
- Критерии приёмки:
  - После POST то же `message` и адрес читаются обратно.
  - Пароль из тела не попадает в выдачу списка и в логи.
- Тесты: api — отправка и чтение.
- Сценарии сбоев: повторная отправка того же текста хранит оба факта отправки, не затирает первый.
- Статус: done

### T-2.3: Мок Direct Debit с настраиваемым кодом
- Модуль: platform-mock, charging
- Требования: REQ-MOCK-002, REQ-MOCK-004, REQ-CHG-009, REQ-CHG-013
- Файлы ТЗ для контекста: `docs/spec/modules/platform-mock.md`, `docs/spec/modules/charging.md`, `docs/spec/open-questions.md` (Q13)
- Зависит от: T-0.1
- Затрагиваемые слои: Presentation мока
- Размер: M
- Что сделать:
  - `POST /caas/direct/debit` принимает поля §D.
  - Код ответа переключается способом из принятого Q13. Минимум `S1000`, `E1326`, `E1308`, `E1337`.
  - Уже виденный `externalTrxId` отвечает `E1337`, без второго успешного списания.
  - Успех `S1000` возвращает `externalTrxId`, `internalTrxId`, `referenceId`, `timeStamp`.
- Критерии приёмки:
  - Каждый из четырёх кодов можно получить на первом запросе с новым ключом.
  - Второй запрос с тем же ключом — `E1337`, даже если конфиг сейчас `S1000`.
  - Новый ключ не считается дублем предыдущего.
- Тесты: api — матрица кодов и дубль ключа.
- Сценарии сбоев: повтор того же ключа после рестарта мока. Если хранилище мока в памяти, рестарт забывает ключ — это дыра для демо идемпотентности. Хранить увиденные ключи так, чтобы рестарт контейнера мока не превращал повтор в новое списание, либо явно записать ограничение в DECISIONS, если пользователь примет более слабый вариант. По умолчанию: ключи живут в той же БД compose.
- Статус: done

### T-2.4: Мок пушит subscription notification
- Модуль: platform-mock, subscription-webhook
- Требования: REQ-MOCK-003, REQ-WH-001, REQ-WH-005
- Файлы ТЗ для контекста: `docs/spec/modules/platform-mock.md`, `docs/spec/modules/subscription-webhook.md`
- Зависит от: T-0.1
- Затрагиваемые слои: Presentation мока
- Размер: S
- Что сделать:
  - Команда или HTTP-ручка мока отправляет на URL сервиса JSON §B.
  - В теле есть `applicationId`, `subscriberId`, `frequency`, `status`, `version`, `timeStamp`.
  - `status` можно выбрать из `REGISTERED | UNREGISTERED | PENDING | CHARGE`.
- Критерии приёмки:
  - Задокументированный вызов мока делает один HTTP POST на сервис.
  - Повтор этой команды шлёт событие ещё раз (дубль — забота сервиса, не мока).
- Тесты: api — мок вызывает тестовый приёмник и тело совпадает с §B.
- Сценарии сбоев: сервис недоступен → мок не падает всем процессом; ошибка доставки видна в ответе ручки.
- Статус: done
